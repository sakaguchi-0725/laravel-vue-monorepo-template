# ADR-0004: api を Http / UseCases / Models の3層にする

## 背景

api は web / admin に REST API を提供する（[ADR-0003](./0003-separate-api-surface-for-web-and-admin.md)）。  
扱う処理は入力の検証、状態の遷移、認可が中心で、計算そのものが複雑になる箇所は現時点でない。  
一方で外部サービスとの連携は複数発生する見込みで、そこはテスト時の差し替えが必要になる。  
本リポジトリはテンプレートであり、最初の実装者以外がこの構成の上に機能を足していく。

## 判断基準

- 処理の複雑さに対して、レイヤーの数と抽象化のコストが見合っていること
- 機能追加時に触るファイルが、レイヤーと型から一意に決まること

## 検討した選択肢

- Http → UseCases → Models の3層とし、永続化は UseCase で Eloquent を直接使う
- オニオンアーキテクチャ（ドメイン層を中心に置き、永続化をリポジトリの interface で反転させる）

## 決定

**Http → UseCases → Models の3層**を採用し、Repository 層を作らず UseCase から Eloquent モデルを直接使う。

オニオンアーキテクチャは永続化の反転とドメインモデルの維持にコストがかかる。  
api は外部サービスとの連携が多いだけでロジック自体は単純なため、そのコストに対する見返りが小さいと判断した。  
依存の反転が必要なのは外部サービスとの境界だけなので、interface は `Externals/` に限って置く。

## 影響

- 良い: 1つの UseCase を読めば、その機能のロジック・認可・トランザクション境界が揃って分かる
- 良い: Eloquent のスコープ・リレーション・キャストをそのまま使え、永続化のための変換コードを書かない
- 悪い: UseCase が Eloquent に直接依存するため、DB 抜きで UseCase を検証できない
- 悪い: 永続化の都合（カラム名・リレーション）が UseCase の記述に現れ、スキーマ変更が UseCase まで波及する
- 悪い: ドメインの不変条件を置く層がないため、同じ検証が複数の UseCase に重複しうる
- 中立: 依存の反転は外部サービス境界にだけ適用する。永続化には適用しない
- 中立: ロジックが複雑化した場合、この構成のままでは受け止められず、層の追加を別途判断することになる
