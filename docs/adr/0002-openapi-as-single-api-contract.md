# ADR-0002: OpenAPI を唯一の API 契約とする

## 背景

api は web と admin の2つのフロントエンドに対して別々のエンドポイント群を提供する。  
両フロントエンドは api の実装を直接参照できないため、リクエスト・レスポンスの形を何らかの定義に依存して組み立てる必要がある。  
フロントの型・モック、api 側のテストがそれぞれ別の根拠を持つと、どれが正なのかを実行時まで判定できない。

## 判断基準

- フロントの型生成と api 側の契約テストが同一の定義から導かれること
- 契約が実装より先に確定し、フロントと api を並行して進められること

## 検討した選択肢

- OpenAPI を唯一の契約とし、スキーマファーストで `docs/api` を先に書く

他案は検討していない。

## 決定

**OpenAPI を唯一の API 契約とする。**

`docs/api/{web,admin}/openapi.yml` を実装より先に書き、フロントの型と api 側の契約テストはそこから導く。

## 影響

- 良い: フロントの型・MSW のモック・api の契約テストがすべて同じ YAML を参照するため、片方だけが契約からずれた状態を機械的に検出できる
- 良い: 契約が先に確定するので、api の実装を待たずにフロントを進められる
- 悪い: エンドポイントの追加・変更のたびに YAML を手で直す工数がかかる
- 悪い: フロントの型は生成物なので、再生成を忘れると契約と実装の間にずれが残る
- 中立: OpenAPI で表現しきれない仕様（条件によって変わるレスポンスなど）は、`docs/design/` の受け入れ基準で補う
