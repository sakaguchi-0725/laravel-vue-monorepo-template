# 設計ドキュメント記述ガイドライン

ユースケース記述（受け入れ基準・事前条件・備考）を書くときの良い例／悪い例集。
`docs/design/{domain}/` 配下のファイルを書く前に必ず参照する。

貫く原則: **ユースケース＝システムの振る舞いを、実装から独立して、具体的かつ曖昧さなく書く。**

---

## 1. 実装詳細を書かない

受け入れ基準・事前条件・備考には、システムの外形的な振る舞いだけを書く。
特定の外部サービス名・API 名・例外名・内部の認証機構（トークン種別・セッション・ハッシュ等）といった実装詳細は持ち込まない。実装は設計が確定した後に決まるものであり、振る舞いの記述を実装に縛らせない。

**悪い例（実装詳細が混入している）:**
- When: `InitiateAuth`(AuthFlow=`USER_PASSWORD_AUTH`, USERNAME=email, PASSWORD, SECRET_HASH) を呼び出す
- Then: Cognito が `NotAuthorizedException` を返し、401 相当を返す
- Then: `AdminGetUser` で `sub` を取得し accounts に INSERT する

**良い例（システムの振る舞いで書く）:**
- When: ログインを実行する
- Then: 認証が拒否され、メールアドレスまたはパスワードが正しくない旨が返る
- Then: アカウントが有効化され、氏名を含むアカウント情報が登録される

判断基準: その記述が「採用する技術を変えたら書き換わる」なら実装詳細。振る舞い（利用者から見た入出力・状態変化）は技術を変えても不変。

---

## 2. 抽象的な数値・回数・期間は具体値を明記する

「有効期限がある」「規定回数以上失敗」といった曖昧表現は、値が分からないとドキュメントとして意味をなさない。
何分で失効・何回失敗で何分ロック、を具体値で明記する。値そのものは決定値として言い切る（「（サンプル値）」等の注記は残さない。ドキュメントの価値を下げるため）。

なお受け入れ基準の本文では「規定回数」「一定時間」のような表現を使ってよいが、**その具体値を備考に必ず定義する**（値変更時に備考だけ直せばよい）。

**悪い例:**
- 送信される認証コードには有効期限がある。
- 同一利用者で短時間に規定回数以上ログインに失敗している。

**良い例（備考に具体値を定義）:**
- 認証コードの有効期限は **3分**。期限切れ後はログインからやり直す。
- ログインに連続 **5回** 失敗すると、同一利用者は以降 **15分** 間ログインを受け付けない。

## 3. 設定・インフラ構成を持ち込まない

事前条件には「そのユースケースが成立するために必要な、利用者・データの状態」だけを書く。
外部サービスの設定手順・構成（エイリアス設定、認証フローの有効化、パスワードポリシー設定など）はユースケースの振る舞いと無関係なので書かない。

**悪い例（構成・設定の記述）:**
- Cognito アプリクライアントで email をサインインエイリアスに設定済み
- パスワードポリシー・`name` 標準属性が有効
- アプリクライアントで `USER_PASSWORD_AUTH` と MFA が有効

**良い例（利用者・データの状態）:**
- 対象メールアドレスが登録済みかつ確認済みのアカウントとして存在する
- 対象メールアドレスがまだ登録されていない

---

## 4. 意味の曖昧な項目・重複を残さない

読み手が「何を指すのか」判断できない項目、他の項目と重複して独立した意味を持たない項目は書かない。
実装の内部事情を抽象化しようとして生まれた、振る舞いとして識別できない概念は削除する。

**悪い例（重複・意味不明）:**
- 認証コードの有効期限は 3分。／ コード入力の受付期間はログイン開始から 15分。
  → 「有効期限」と「受付期間」が重複し、後者が何を指すか（画面の話か等）読み取れない。実装（セッション失効）の抽象化にすぎず、振る舞いとして意味を持たない。

**良い例（一本化）:**
- 認証コードの有効期限は 3分。期限切れ後はログインからやり直す。

判断基準: その異常系／制約が、利用者から見て他と区別できる固有の振る舞いか。区別できないなら統合・削除する。

## 5. シナリオタイトル

各シナリオには必ず **「〇〇の場合、〇〇となること」** 形式の太字タイトルを付ける。
Given/When/Then とは別に、1行で振る舞いを読み取れるサマリーとして機能させるため。

```
**正常系: カートに在庫のある商品がある場合、注文が正常に作成されること**
- Given: ...
- When: ...
- Then: ...

**異常系: 権限のない一般社員が操作しようとした場合、操作が拒否されること**
- Given: ...
- When: ...
- Then: ...
```

### 冗長な言い回しを避ける

「〇〇した場合、〇〇となること」は **条件によって結果が分岐するとき** の形式。操作の動詞と結果の動詞がほぼ同義語になる（＝分岐の意味がない主正常系）ケースにこの形式を使うと、同じことを二度言う不自然な日本語になる。その場合は **「{アクター}が{対象}を{動詞}できること」** と言い切る。

**悪い例（動詞が同義反復している）:**
- 「マネージャーが取引先を作成した場合、取引先が作成されること」（作成≒作成）
- 「マネージャーが取引先に担当者を追加した場合、担当者が登録されること」（追加≒登録）
- 「マネージャーが取引先を削除した場合、取引先が論理削除されること」（削除≒論理削除）

**良い例（アクターが対象に対して直接その操作を行える、と言い切る）:**
- 「マネージャーが取引先を作成できること」
- 「マネージャーが取引先に担当者を登録できること」
- 「マネージャーが取引先を論理削除できること」

判断基準:
- 分岐がない主正常系（操作＝結果） → **「{アクター}が{対象}を{動詞}できること」** に言い換える
- 前提条件によって結果や挙動が変わる（0件なら空配列、既存データがあれば複数件になる等） → 「〇〇の場合、〇〇となること」を維持する

---

## 6. 粒度：振る舞いレベルで書く（入力バリデーションの細部は書かない）

受け入れ基準はシステムの**振る舞い**を記述する。入力バリデーション（必須項目未入力・フォーマット不正など）の細部は含めない。

**書く異常系の例:**
- 権限のないロールが操作しようとした → 拒否される
- 存在しない対象（ID）にアクセスした → 404 または非公開
- 既に処理済みの対象に再度操作した → エラーで弾く

**書かない異常系の例:**
- 名前フィールドが空白のまま送信した → バリデーションエラー
- メールアドレスの形式が不正 → エラーメッセージが出る
- パスワードがポリシー（長さ・文字種）を満たさない → エラー

## 7. 文末に半角スペース2つを付ける（プレビューでの改行）

概要・備考など複数の文が続く箇所は、各文末（`。`）の直後に **半角スペース2つ** を付ける。Markdown のハードブレークになり、プレビュー時に文ごとに改行されて読みやすくなる。1文で完結する箇所には不要。

例（`␣` は半角スペース。実際には見えない）:

```
入力された氏名は、認証コードの確認完了まで保持する。␣␣
本登録時にアカウント情報へ反映する。␣␣
ロールは受け取らず general 固定とする。
```

上記はプレビューで3行に分かれて表示される。半角スペース2つが無いと、Markdown では連続する行が1段落に連結され改行されない。

## 8. 判断を先送りしない（「実装時に検討」を書かない）

設計ドキュメントは**決まったこと**を書く場所であり、決まっていないことを書き留めておく場所ではない。
「実装時に検討する」「別途決める」「TBD」「要検討」といった先送りの記述は書かない。設計が確定していない状態のまま実装に着手すると、判断が実装者（人間・AI を問わず）に暗黙で委ねられ、ドキュメントに残らない。また先送りメモは実装後に更新されず陳腐化し、ドキュメントの信頼性を下げる。

判断が必要だと気づいた時点で、**その場で決めてドキュメントに書き切る**。決められないなら、生成前の確認（Step 2）でユーザーに問う。

**悪い例（判断の先送り）:**
- 失敗時のリカバリ方針（再試行・補償）は実装時に検討する。
- 同時更新時の競合制御は後で決める。
- 通知の送信タイミングは TBD。

**良い例（振る舞いとして決め切る）:**
- 退会の記録と認証の無効化は、両方が成功したときにのみ退会を成立させる。片方が失敗した場合は退会前の状態に戻す。
- 同時更新が発生した場合、後着の更新を拒否し、最新の状態の再取得を促す。

決め切った内容が「エラー時にどうなるか」であれば、備考ではなく **受け入れ基準の異常系シナリオ** として書けることが多い。振る舞いとして検証可能になるため、そちらを優先する。

なお「スコープ外」「別ユースケースで扱う」は先送りではなく**範囲の確定**なので書いてよい。両者の区別は、読み手がその記述だけでシステムの振る舞いを一意に決められるかどうか。

---

## 9. 備考は書くことがあるときだけ書く

「備考」は任意セクション。テンプレートに枠があるからといって埋めない。書くべき補足が無ければ**セクションごと削除する**。
中身の無い備考は、読み手に「ここに何か重要なことが書いてある」と期待させて裏切るぶん、無いより悪い。

判断基準は **他のセクションから読み取れない情報か** の一点。

**書く:**
- 受け入れ基準に現れる「規定回数」「一定時間」等の具体値の定義（§2）
- 制約・ビジネスルールと、**その理由**
  - 「`role` は本ユースケースでは変更できない（権限昇格を防ぐため）」← 理由が他のどこにも無い
  - 「メールアドレスの登録有無を応答で区別しない（利用者列挙の防止）」← 同上
- 明示的に除外する対象と、その代替への導線
  - 「詳細項目（`email` 等）は返さない。詳細が必要な場合は UC-002 を利用する」

**書かない:**
- 概要・アクター・受け入れ基準を読めば分かる内容
  - 概要に「認証済みユーザーが**自身の**プロフィールを取得する」、アクターに「本人」とある UC で、備考に「本人のみが取得対象。他ユーザーの参照はスコープ外」と書く → 三重の重複で情報量ゼロ
  - 概要に「退会後もアカウント情報は保持される」とある UC で、備考に「物理削除しない」と書く → 同じことの言い換え
- 決まっていない事項の書き置き（§8）

概要と備考で同じ制約に触れてしまった場合は、**理由が書ける備考の側に寄せ、概要から落とす**。概要は「何をするか」を述べる場所であり、制約とその根拠は備考の担当。
