# design-docs スキル

ユーザーから渡された要件・機能概要を分析し、`docs/design/{domain}/` 以下の設計ドキュメントを生成する。

## ゴール

- ユーザーの入力（チャット・mdファイル・箇条書きなど）をもとにドメイン設計ドキュメントを作る
- 受け入れ基準は Given/When/Then 形式で書く（正常系・異常系を分けて網羅する）
- 情報が足りない部分はまとめて質問してから生成する（一問一答ではなく一括確認）

---

## 記述ガイドライン（必読）

受け入れ基準・事前条件・備考の書き方は [`references/guidelines.md`](./references/guidelines.md) に良い例／悪い例をまとめてある。ドキュメントを書く前（Step 3）に必ず読み、全項目に従う。要点:

1. 実装詳細（外部サービス名・API 名・例外名・内部認証機構）を書かない。システムの振る舞いだけを書く
2. 抽象的な数値・回数・期間は具体値を明記する（決定値として言い切り、備考に定義）
3. 事前条件に設定・インフラ構成を持ち込まない（利用者・データの状態だけ）
4. 意味の曖昧な項目・他と重複する項目を残さない
5. シナリオタイトルは「〇〇の場合、〇〇となること」形式。ただし動詞が同義反復する主正常系は「{アクター}が{対象}を{動詞}できること」と言い切る
6. 入力バリデーションの細部は書かない（振る舞いレベルの粒度）
7. 複数文が続く箇所は文末（。）に半角スペース2つを付け、プレビューで改行させる
8. 判断を先送りしない（「実装時に検討」「TBD」を書かない）。その場で決め切り、エラー時の振る舞いは異常系シナリオとして書く。不明点はユーザーに確認すること。
9. 備考は他セクションから読み取れない情報があるときだけ書く。無ければセクションごと削除する

---

## Step 1: 入力の読み取り

ユーザーがファイルパスを渡した場合は Read して内容を把握する。
チャットテキストの場合はそのまま分析する。

以下の要素を識別する:

- **ドメイン名**: 集約・機能の中心になる概念（例: `order`, `user`, `payment`）
- **ユースケース**: 誰が・何をする、のペアで列挙（例: 「購入者が商品を注文する」）
- **アクター**: システムを操作する人・外部システム
- **API**: 関連するエンドポイントや仕様書への言及

---

## Step 2: 不足情報を一括確認

生成前に必ず不足情報をまとめて質問する。**1つずつ聞かず、まとめて提示する。**

典型的な確認ポイント:

- ドメイン名が不明 → 推定した候補を提示して確認（例:「`order` ドメインとして進めてよいですか？」）
- ユースケースの主語（アクター）が不明 → 誰が操作するか確認
- 異常系が書かれていない → 代表的な異常系を提案して取捨選択してもらう
- API仕様書リンクが必要か → `docs/api/web/`（利用者向け）／`docs/api/admin/`（管理者向け）のどちらへのリンクを含めるか確認

質問のフォーマット例:

```
以下を確認させてください:

1. ドメイン名は `order` で合ってますか？
2. 「注文キャンセル」ユースケースのアクターは「購入者」のみですか？
3. 異常系として以下を追加してよいですか？
   - 在庫切れで注文できない場合
   - 支払いが失敗した場合
4. index.md に `docs/api/web/` へのリンクを含めますか？（管理者向けなら `docs/api/admin/`）
```

ユーザーの回答を受けて、Step 3 に進む。

---

## Step 3: ファイル生成

**生成前に [`references/guidelines.md`](./references/guidelines.md) を必ず読み、全項目に従って書く。**

`docs/design/{domain}/` に以下のファイルを生成する。

- `index.md`
- `{use-case}.md`（ファイル名はケバブケース・動詞-名詞: 例 `create-order.md`）

テンプレートは以下を参照:

- [`references/index-template.md`](./references/index-template.md)
- [`references/usecase-template.md`](./references/usecase-template.md)

### フローセクションの記載基準

`{use-case}.md` のフローセクションは任意。以下の条件を満たす場合に追加する:

- DB 以外の外部システム（Cognito、Google、決済サービス等）が絡む
- 複数のアクターが往復でやり取りし、処理の順序・タイミングが重要
- フロントエンドとバックエンドの間で複数回のリクエストが発生する

単純な取得・登録（一覧取得、詳細取得、DB への単純な INSERT 等）はフローなしでよい。

## 命名規則

| 対象                   | 規則                    | 例                                          |
| ---------------------- | ----------------------- | ------------------------------------------- |
| ディレクトリ名         | ケバブケース            | `order`, `user-management`                  |
| ユースケースファイル名 | ケバブケース・動詞-名詞 | `create-order.md`, `cancel-subscription.md` |
| ユースケースID         | `UC-{3桁連番}`          | `UC-001`, `UC-002`                          |

## 品質チェック（生成後に確認）

- [ ] [`references/guidelines.md`](./references/guidelines.md) の全項目に従っている（実装詳細を書かない・具体値を明記・設定情報を持ち込まない・曖昧/重複項目なし・判断を先送りしない）
- [ ] 受け入れ基準は正常系と異常系が両方ある
- [ ] Given/When/Then がそれぞれ具体的な状態・操作・結果になっている（抽象的な記述になっていない）
- [ ] index.md のユースケース一覧と実際のファイルが対応している
- [ ] ファイル名がケバブケースになっている
- [ ] 「備考」「フロー」は任意セクション。書くべき内容が無い場合はセクションごと省いている
