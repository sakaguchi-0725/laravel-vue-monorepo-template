# ADR 判定基準

Step 1（ADR 化すべき決定か）と Step 3（scope の決定）で使う判断基準。

貫く原則: **ADR は「アーキテクチャ的に重要な決定」だけを記録する場所であり、汎用のドキュメント置き場ではない。**

ADR を何にでも使うと、数百件の「メモ」に本当の決定が埋もれて、決定ログとして機能しなくなる。

---

## A. ADR を書くべき決定か（Step 1）

### 対象になるもの

以下の5分類のいずれかに当てはまり、かつ**後から変えるコストが高い**なら ADR にする。

| 分類 | 判断の観点 | このリポジトリでの例 |
| --- | --- | --- |
| 構造 | システムをどう分割・配置するか | FSD のレイヤ構成、apps/api のレイヤ構成、apps / packages の分割方針 |
| 非機能要件 | 品質特性をどう担保するか | 認証・認可方式、レート制限、可観測性、エラー監視 |
| 依存関係 | 何に依存し、どう結合するか | フロント（web / admin）と api の結合方式、packages/ 経由の共有、外部サービス（認証基盤・決済）への依存 |
| インターフェース | 外部と交わす契約をどう定めるか | API エラーレスポンス形式、OpenAPI を web / admin / shared に分ける方針、認証ヘッダの規約 |
| 構築技術 | 何を使って作るか | Laravel / Vue / Vite / pnpm workspace / mise の採用、テスト戦略 |

### 対象にならないもの

以下は ADR にしない。それぞれ担当するドキュメントが別にある。

| 依頼の例 | 実際の担当 |
| --- | --- |
| ボタンコンポーネントの props 設計 | 実装（必要ならコード内コメント） |
| ログイン失敗時に返すエラーコード | `docs/api/shared/error.yml` |
| `POST /accounts` のリクエストスキーマ | `docs/api/{web,admin}/openapi.yml` |
| ローカル環境の起動手順 | `README.md` |
| 特定関数のリファクタ方針 | ADR 不要（PR の説明で足りる） |
| コーディング規約（命名・import 順） | `.claude/rules/` |
| Vue コンポーネントの書き方 | `.claude/rules/frontend/vue.md` |

### 迷ったときの判定

次の3つすべてに「はい」なら ADR にする。

1. **半年後の担当者が「なぜこうなっているのか」と聞く可能性があるか**
2. **後から変えるとコード全体に波及するか**（1ファイルの修正で戻せるなら不要）
3. **他の選択肢が実在したか**（選択肢が1つしかなかったなら、それは決定ではなく前提）

### 対象外だったときの差し戻し方

黙って別の場所に書かず、**なぜ ADR にしないのか・どこに書くべきか**を示して終了する。判断を勝手に肩代わりすると、
ユーザーが「ADR に残した」と誤認したまま進んでしまう。

例文:

```
これは ADR の対象外です。

「ボタンの props 設計」は1コンポーネント内で完結し、後から変えても波及しません。
ADR は構造・非機能要件・依存関係・インターフェース・構築技術のうち、
変更コストが高い決定だけを記録する場所です。

書くとすれば実装時のコメント、または共通コンポーネントの方針として
.claude/rules/frontend/vue.md への追記が適切です。そちらで進めますか？
```

## B. scope の判定（Step 3）

| 値 | 対象 | 例 |
| --- | --- | --- |
| `web` | apps/web 内で完結する | 状態管理ライブラリ、CSS 手法、ルーティング、ディレクトリ構成 |
| `admin` | apps/admin 内で完結する | 管理画面固有の権限表現、一覧・検索 UI の方針 |
| `api` | apps/api 内で完結する | レイヤ分割、Eloquent / クエリビルダの使い分け、DB スキーマ方針、ログ出力形式 |
| `shared` | 複数のアプリが拘束される | API エラー形式、認証方式、OpenAPI からの型生成、packages/ui の共通コンポーネント方針 |
| `infra` | アプリケーションの外側 | CI 構成、Docker、モノレポツール（mise / pnpm workspace）、デプロイ先 |

### 判定の順序

1. **アプリのコードの話ではない**（CI・コンテナ・デプロイ・開発ツール）→ `infra`
2. **複数のアプリ、または `packages/` 配下がその決定に従う必要がある** → `shared`
3. それ以外 → 拘束されるアプリで `web` / `admin` / `api`

「どのディレクトリのファイルが変わるか」ではなく、**どれが決定に拘束されるか**で判断する。

### 迷いやすい境界例

| 決定 | scope | 理由 |
| --- | --- | --- |
| 認証トークンの保存場所（Cookie / localStorage） | `shared` | フロント側の保存方法に見えるが、api 側の発行方式（`Set-Cookie` か レスポンスボディか）と対で決まる |
| OpenAPI から型を生成する | `shared` | 生成先は web / admin の両方。片方だけ変えると契約が壊れる |
| API エラーレスポンスの形式 | `shared` | api が返し、web と admin がその形に依存する |
| web と admin で共通のフォーム部品を packages/ui に置く | `shared` | 両アプリが同じ実装に拘束される |
| web のキャッシュ戦略 | `web` | api は関知しない（キャッシュヘッダを api が制御するなら `shared`） |
| admin の一覧画面をサーバーサイドページネーションにする | `shared` | api のエンドポイント設計とセットで決まる |
| DB のマイグレーション管理方法 | `api` | web / admin は影響を受けない |
| pre-commit に lint を入れる | `infra` | 全アプリのコードに走るが、決定に拘束されるのは開発フローであってアプリではない |

`shared` にするか迷ったら `shared` にする。片側に寄せて分類ミスをすると、もう片方の担当者が読み落とす。
