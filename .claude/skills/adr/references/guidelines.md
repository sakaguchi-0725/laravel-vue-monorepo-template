# ADR 記述ガイドライン

ADR 本文を書くときの良い例／悪い例集。`docs/adr/NNNN-*.md` を書く前に必ず参照する。

貫く原則: **ADR は「決定の報告」であって「指示書」でも「宣伝」でもない。**

読み手は半年後の担当者。その人が知りたいのは手順ではなく、**どんな制約の下で何を捨てて何を選んだか**。

---

## 1. 1 ADR = 1 決定

複数の決定を1本に詰め込むと、それぞれ別のタイミングで陳腐化するのに一括でしか更新できなくなる。
ステータスも1つしか持てないため、「片方だけ superseded」を表現できない。

**悪い例（複数の決定が混在）:**

> # ADR-0003: バックエンド構成を決定する
>
> Go + Echo を採用し、ORM は sqlc、ログは slog、テストは testify を使う。

**良い例（分割する）:**

- `0003-adopt-go-echo.md`
- `0004-adopt-sqlc.md`
- `0005-use-slog-for-structured-logging.md`

判断基準: それぞれが独立して覆りうるなら別 ADR。同時にしか変わりえないなら1本でよい。

---

## 2. 背景には中立の事実だけを書く

「背景」は決定を迫った状況の説明であり、結論の助走ではない。
売り込みの言葉が入ると、読み手は「本当に比較検討したのか」を疑う。

**悪い例（宣伝・断定が混じっている）:**

- Echo は Go で最速のフレームワークであり、モダンな開発には必須である。
- sqlc を使えば型安全性が劇的に向上し、バグが激減する。

**良い例（事実と制約）:**

- server は REST API のみを提供し、GraphQL や gRPC の要件はない。
- チームに Go の実務経験者は1名で、残り2名は TypeScript が主戦場。
- 開発期間は3ヶ月で、フレームワークの学習に割ける時間は限られている。

判断基準: その文が「計測値・制約・体制」のいずれでもなく、形容詞で価値を主張しているなら宣伝。

---

## 3. 「影響」には悪い影響を必ず書く

良い面しか書かれていない ADR は、読み手にとって判断材料にならない。
トレードオフの無い技術選定はほぼ存在せず、書かれていないなら「検討していない」と読まれる。

**悪い例（良い面だけ）:**

```
## 影響

- 良い: 型安全になる
- 良い: 開発速度が上がる
- 良い: 保守性が高まる
```

**良い例（コストを言い切る）:**

```
## 影響

- 良い: SQL とレスポンス型が生成物として一致し、手書きのマッピングが不要になる
- 悪い: スキーマ変更のたびに生成コマンドの実行が必要で、忘れるとビルドが通らない
- 悪い: 動的なクエリ組み立て（検索条件の可変結合）は sqlc の外で書く必要がある
- 中立: マイグレーションツールは別途選定が必要（本 ADR の対象外）
```

「悪い」が思いつかない場合は、学習コスト・依存の増加・移行コスト・ロックインを疑う。

---

## 4. 「検討した選択肢」には実在した案だけを書く

比較のために当て馬を並べると、ADR そのものの信頼性が失われる。
実際には検討していない案を「劣っている」と書くのは、後から見れば嘘でしかない。

**悪い例（明らかな当て馬）:**

> - Echo
> - 生の `net/http` にすべて自前実装
> - PHP で書き直す

**良い例（実際に比較した案）:**

> - Echo
> - Gin
> - chi + 標準ライブラリ

案が1つしか無かったなら、1つだけ書く。「他を検討しなかった」ことも情報として正しい。

---

## 5. `accepted` 後は本文を書き換えない

ADR の価値は「その時点で何を知っていて、どう判断したか」が残ること。
後から書き換えると、当時の判断が見えなくなり、履歴としての意味を失う。

**悪い例:** ADR-0003「Echo を採用する」の本文を書き換えて Gin 採用に直す。

**良い例:**

1. ADR-0009「Gin へ移行する」を新規作成し、`supersedes: 0003` を設定
2. ADR-0003 の front matter を `status: superseded` / `superseded-by: 0009` に更新（**本文は触らない**）

誤字の修正だけは例外。

---

## 6. 手順・設定方法を書かない

ADR は「なぜ」を記録する。「どうやるか」は README・OpenAPI・コード側の担当。
手順を書くと ADR が陳腐化し、しかも不変であるべき ADR を更新したくなってしまう。

**悪い例:**

> ## 決定
>
> sqlc を採用する。導入手順は以下のとおり:
>
> 1. `mise install sqlc`
> 2. `sqlc.yaml` を作成し、`engine: postgresql` を指定
> 3. `queries/` に SQL を配置して `sqlc generate`

**良い例:**

> ## 決定
>
> **sqlc** を採用する。
>
> SQL を直接書きつつ Go の型を生成でき、動的クエリの少ない本プロジェクトの用途に合うため。

---

## 7. 現在の全体構成を書かない

ADR は「ある時点の1決定」の記録であり、システムの現状を表す文書ではない。
全体構成図を ADR に置くと、他の ADR が積み重なった瞬間に古くなる。

**悪い例:** ADR に全レイヤの構成図・ディレクトリツリー・ER 図を貼る。

**良い例:** その決定に直接関わる範囲だけに言及する。全体像が必要なら別途 README や構成図ドキュメントに置き、ADR からはリンクする。

---

## 8. 1〜2ページに収める

10ページの ADR は読まれない。読まれない決定ログは存在しないのと同じ。

超えた場合、原因はほぼ次のいずれか。

- 決定が複数混ざっている（→ §1 で分割）
- 実装詳細・手順が入っている（→ §6 で削除）
- 各案の評価が長すぎる（→ 決め手になった論点だけに絞る）

---

## 9. 決めたその時に書く

数ヶ月後に書く ADR は、形式は ADR でも中身が別物になる。背景は記憶からの再構成になり、
却下した案は忘れられ、「影響」が予測ではなく既に起きた結果の説明になる。

やむを得ず遡って記録する場合は、背景に**遡って書いた旨と、当時分かっていなかったこと**を明記する。

> ## 背景
>
> （本 ADR は採用から約1年後に遡って記録した。当時の議事録が残っていないため、
> 検討した選択肢は当時の関係者への確認に基づく。）

---

## 10. 文末に半角スペース2つを付ける（プレビューでの改行）

背景・影響など複数の文が続く箇所は、各文末（`。`）の直後に **半角スペース2つ** を付ける。
Markdown のハードブレークになり、プレビュー時に文ごとに改行されて読みやすくなる。1文で完結する箇所には不要。

`docs/design/` 配下と同じ規約。
