# 不足情報の一括確認フォーマット

Step 4 で使う。

ADR の価値の大半は **「他に何を検討して、なぜそれを捨てたか」** と **「何を諦めたか」** にある。
そしてこの2つは、コードにもドキュメントにも残っていない。ユーザーの頭の中にしかない。

ここを聞かずに書くと、メリットだけが並んだ ADR になる。それは決定の記録ではなく、後付けの正当化にすぎず、
半年後に「なぜこれを選んだのか」を答えられない。

**1問ずつ聞かず、1メッセージにまとめて提示する。**

---

## 聞くべき項目

| 項目 | なぜ聞くか | 質問例 |
| --- | --- | --- |
| 検討した他の案 | 選択肢が書かれていない ADR は、同じ議論を再燃させる | 「{案A} のほかに {案B}・{案C} も検討しましたか？」 |
| 却下理由 | 却下理由こそが再提案を防ぐ | 「{案B} を採らなかった決め手は何ですか？」 |
| 判断基準 | 何を優先したかが分かると、将来の別の決定にも使える | 「何を最優先しましたか（開発速度 / 運用コスト / 学習コスト / 型安全性 / チームの経験）」 |
| 受け入れたコスト | 「影響」の悪い面を埋めるために必須 | 「この選択で諦めたこと・将来困りそうなことはありますか？」 |
| status | `proposed` と `accepted` では読み手の扱いが変わる | 「`accepted`（決定済み）でよいですか、`proposed`（提案段階）ですか？」 |
| 置き換え対象 | Superseded の連鎖を切らさない | 「既存の ADR-XXXX を置き換えますか？」（関連する ADR がある場合のみ） |

すでにユーザーの入力や会話から読み取れる項目は聞かない。空欄の項目だけをまとめる。

---

## 提示のしかた

推測できる部分は**こちらの推測を書いて確認する形**にする。ゼロから答えさせると回答が重くなり、返ってこない。

```
ADR を書く前に以下を確認させてください。

1. 検討した他の案は次のとおりで合っていますか？
   - 案B: {推測した案}
   - 案C: {推測した案}
   他にあれば教えてください。無ければ「{案A} のみ検討」として書きます。

2. 案B を採らなかった決め手は何でしたか？

3. 判断で最優先したのはどれですか？（複数可）
   開発速度 / 運用コスト / 学習コスト / 型安全性 / チームの経験

4. この選択で諦めたこと・将来困りそうなことはありますか？
   （なければ「なし」で構いませんが、トレードオフのない選択はほぼありません）

5. status は `accepted` でよいですか？（提案段階なら `proposed`）
```

---

## 回答が得られなかったとき

**推測で埋めない。** 特に「検討した選択肢」を推測で水増しすると、実際には検討していない案が
当て馬として並ぶことになり、ADR の信頼性が根本から失われる。

| 項目 | 回答が無い場合の扱い |
| --- | --- |
| 検討した他の案 | 実在した案だけを書く。1つしかなければ「検討した選択肢」に1件だけ書く |
| 却下理由 | 案は列挙し、理由の行は書かない（空欄のまま残さず、行ごと省く） |
| 判断基準 | 「判断基準」セクションごと省く |
| 受け入れたコスト | **ここだけは省かない。** 技術的に自明なコスト（学習コスト・依存の増加・ロックイン等）を書き、ユーザーに確認してもらう |
| status | `proposed` にする（勝手に `accepted` にしない） |

「実装時に検討」「TBD」「要検討」は書かない。決まっていないなら `status: proposed` で出し、
決まった時点で `accepted` に更新する。
