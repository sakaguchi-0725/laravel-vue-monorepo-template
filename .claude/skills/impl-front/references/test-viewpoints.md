# テスト観点

- storybookによるテストのみ行い、composableのテストは行わない
- storybookのテストは画面単位で行い、play関数で検証する
- zodスキーマ・表示用の整形関数の単体テストも書かない
- 全観点を書く必要はない。画面に該当しない観点は省く

## 本数の目安

- 取得系の画面: 3本（データあり / データなし / API失敗）
- フォームの画面: 4本（初期表示 / バリデーションエラー / 送信成功 / 送信失敗）
- 画面遷移がある場合は遷移ごとに1本追加する

## 観点カタログ

### 主要フロー（正常系）

- 画面の主目的の操作が最後まで通ること
- 入力 → 送信 → 期待する結果（次の画面に遷移する、一覧が更新される等）

### 入力バリデーション

- 必須・形式・桁などの不正入力でエラーが表示され、送信されないこと
- バリデーションルールを網羅する必要はない。代表的な1〜2ケースに留める

### APIエラー表示

- サーバーが4xx を返した時、ユーザー向けのエラーメッセージが表示されること
- 文言は固定値ではなく、モックが返した `message` と一致することを確認する

### 空状態・初期表示

- データ0件や初期状態で表示が崩れないこと
- 空メッセージ・プレースホルダが表示されること

### 画面遷移

- リンク・ボタン・送信成功後の遷移先が正しいこと
- `@/shared/test` の `expectRoute(canvasElement, path)` で遷移後のパスを検証する

### 権限・状態差分

- ログイン有無・ロール・データの状態で、表示や操作可否が変わる場合、その分岐が正しいこと

### アクセシビリティ

- ラベルとフォーム部品が対応し、`getByRole` / `getByLabelText` でアクセシブルに操作できること

---

## 実装のヒント

- APIのモックは `@/shared/api/mocks` の `http`（openapi-msw）で書き、`parameters.msw.handlers`
  に渡す。全 story 共通のものは `src/shared/api/mocks/handlers.ts` に置く
- ルート名を持つ画面は `parameters.initialRoute` に渡す（`.storybook/preview.ts` が `router.replace` する）
- テストユーティリティは `storybook/test` から import する（`within` / `userEvent` / `expect` / `fn` / `waitFor`）
- 非同期の表示は `waitFor` / `findBy*` で待つ
- 具体的な書き方は [`guidelines.md`](./guidelines.md) の「Storybook」を参照
