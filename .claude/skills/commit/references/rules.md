# メッセージ構造

Conventional Commits 1.0.0 に準拠する。

```
<type>[(scope)]: <description>

<body>
```

footer は書かない。issue 参照・`BREAKING CHANGE:`・`DEPRECATED:` のいずれも使わない。
ハーネスが付与する `Co-Authored-By:` トレーラーは末尾に残す。

## ヘッダー

| 要素 | ルール |
| --- | --- |
| type | 必須。小文字。「タグ」セクションから選ぶ |
| scope | 任意。括弧内に影響範囲。付け方は下記 |
| 区切り | コロン + 半角スペース1つ |
| description | 必須。日本語。言い切りの形。文末に句点を付けない |
| 長さ | 全角を2文字と数えて 50 カラム目標・72 カラム上限 |

description は「〜を追加」「〜を修正」「〜にする」のような言い切りの形で書く。
「〜した」「〜しました」のような過去形・丁寧形は使わない。

```
OK: feat: 共通 UI パッケージ @repo/ui を追加
OK: fix: FSD の境界ルールが機能していない問題を修正
OK: chore: pnpm の catalogMode を strict にする
NG: feat: 共通 UI パッケージ @repo/ui を追加しました
NG: fix: 境界ルールのバグを直した
NG: feat: ボタンコンポーネントの追加。
NG: update: いろいろ修正
```

## scope

変更が単一のワークスペースパッケージに収まるときだけ付ける。複数パッケージを横断する
変更やルート設定の変更では省略する。迷ったら省略する。

使う語彙はディレクトリ名に合わせる: `api` / `web` / `admin` / `ui` / `eslint-config`

```
OK: feat(ui): アイコンボタンを追加
OK: fix(api): 予約一覧の N+1 クエリを解消
OK: feat: admin と web を FSD 構成にする
OK: chore: Prettier を導入
NG: feat(web,admin): FSD 構成にする
NG: feat(packages/ui): アイコンボタンを追加
NG: chore(root): Prettier を導入
```

## body

ヘッダーとの間に空行を1行入れる。

docs / style 以外のコミットでは原則書く。ヘッダーだけで意図が完結する些末な変更
（typo 修正、依存のバージョン上げ、フォーマッタの適用）では省略してよい。

次の3つを、上から順に、必要なものだけを空行で区切って並べる。

1. 背景と理由（散文）— 何が問題だったか、変更前はどう動いていたか、なぜこの解き方を
   選んだか。fix なら根本原因を書く
2. 変更点の列挙（箇条書き）— 変更が複数の関心事にまたがるときだけ。1つなら書かない
3. 注意事項（散文）— 今後この箇所を触る人が踏みうる落とし穴、既知の制約

全角を2文字と数えて 72 カラムで折り返す。

```
OK:
fix: eslint-config で node:path の型が解決できない問題を修正

TypeScript 6 は node_modules/@types を自動で読み込まなくなったため、
@types/node を追加するだけでは node:path の型が見つからない。

- @types/node を devDependencies に追加
- tsconfig.json の types に node を明示
```

```
NG:
fix: eslint-config で node:path の型が解決できない問題を修正
@types/node を追加し、tsconfig.json の types に node を明示した。
```

## 破壊的変更

`!` も `BREAKING CHANGE:` フッターも使わない。body に何が壊れるか・呼び出し側が何を
すべきかを書く。移行手順まで具体的に書く。

```
OK:
refactor(ui): PrimaryButton の size プロパティを削除

variant で見た目を決める方針にしたため、size による分岐が二重管理になっていた。

size を渡している呼び出し箇所は class での指定に置き換える必要がある。
現時点の呼び出し元は apps/web のサンプルフォームのみで、あわせて修正済み。
```

# タグ

commitlint の config-conventional が許可する11種類を語彙とする。これ以外は使わない。

| type | 使う場面 | 判断の観点 |
| --- | --- | --- |
| `feat` | 機能の追加 | ユーザー（利用者・呼び出し側）から見てできることが増えたか |
| `fix` | バグ修正 | 壊れていた挙動が直ったか |
| `refactor` | 内部構造の変更 | 外から見た挙動が完全に同一か |
| `perf` | パフォーマンス改善 | 挙動は同じで速く・軽くなったか |
| `style` | 整形のみ | フォーマッタ／リンタが直す範囲だけか |
| `test` | テストの追加・修正 | 変更がテストコードに閉じているか |
| `docs` | ドキュメントのみ | 変更が文書に閉じているか |
| `build` | ビルド・実行に必要な構成の変更 | アプリのビルドや動作そのものに影響するか |
| `ci` | CI 設定・スクリプト | CI パイプラインの話か |
| `chore` | 上記に当てはまらない雑務 | 他の10個が全部外れたか |
| `revert` | 打ち消し | 下記の専用フォーマットを使う |

## 判断に迷う境界

type は「変更したファイルの場所」ではなく「外から見た振る舞いがどう変わったか」で決める。

- fix と refactor — 挙動が変わったなら fix、変わっていないなら refactor。
  「バグを直すためにリファクタもした」場合は「コミット粒度」に従って分割する。
  分割できないなら主目的で判定して fix
- refactor と style — コードの構造や意味を変えたなら refactor。フォーマッタが直す範囲
  （改行・空白・引用符）だけなら style
- feat と refactor — 既存の呼び出し側から見て新しくできることが増えていなければ
  refactor。内部に新しいクラスやモジュールを足しても、公開される振る舞いが同じなら
  feat にしない
- build と chore — アプリのビルド・実行に必要なら build（本番依存の追加、Vite や
  Dockerfile の設定）。開発時だけのツールなら chore（Prettier、ESLint、エディタ設定）。
  重なる場合は「今解決しようとしている側」を選ぶ
- docs — README、`docs/` 配下、`.claude/rules` や `.claude/skills` などの指示
  ドキュメント、OpenAPI 定義。コード中のコメントだけを直した場合も docs
- chore は他の10個を一通り当ててから選ぶ

## revert

打ち消しには専用の形式を使う。

```
OK:
revert: feat: 共通 UI パッケージ @repo/ui を追加

This reverts commit 4b2dafe.

admin 側のビルドが解決できない循環参照を生むため、構成を見直して入れ直す。
```

# コミット粒度

次の3条件を満たすものを1コミットとする。

1. 1つの論理的な変更単位に閉じている
2. そのコミット単体でリポジトリが動作する（lint / 型チェック / テストが通る）
3. 関心事を混ぜていない（整形とロジック、機能追加とリファクタを同居させない）

行数は基準にしない。判断基準は「余分な変更が混ざっていないか」の一点。
`feat: admin と web を FSD 構成にする` のように多数のファイルを触っても、
それが1つの論理的変更なら分割しない。

## 分割すべきパターン

以下が同じ差分に混ざっていたら分割する。

- 機械的変更と本質的変更 — 一括リネーム、フォーマッタの適用、自動修正は先に単独
  コミットで通し、ロジック変更を別コミットにする。
  例: `chore: Prettier を導入` → `style: Prettier で既存ファイルを整形`
- 依存の追加と、それを使う実装 — パッケージを足しただけで動作が変わらないなら分ける。
  どちらか一方だけでは動かない場合は同じコミットにする
- 無関係な複数の修正 — たまたま同じ作業中に見つけた別のバグは別コミットにする
- リファクタと機能追加 — 「足す前に整える」順で2コミットに分ける

## 分割しないパターン

- 1つの機能に必要な複数レイヤーの変更（ルーティング + コンポーネント + スキーマ）は
  1コミットにする
- 設定ファイルと、その設定がないと動かないコードは1コミットにする
- 「ファイルが多いから」という理由だけで分割しない

## 判断の手順

1. `git status` / `git diff` で未コミットの変更を全部把握する
2. 変更を「なぜこれを変えたか」の理由でグルーピングする。理由が違うものは別コミット
3. 各グループに type を1つだけ割り当てられるか確かめる。2つ以上の type が思い浮かぶ
   グループは分割する
4. 各グループ単体で lint と型チェックが通る順序に並べる

# ブランチ命名規則

```
<type>/<kebab-case-summary>
```

`<type>` はコミットの type と同じ語彙を使う。そのブランチで作る主要なコミットの type に
合わせる。`<kebab-case-summary>` は変更内容を英小文字とハイフンで簡潔に表す。

```
OK: feat/ui-icon-button
OK: fix/fsd-boundary-resolver
OK: docs/frontend-coding-rules
OK: refactor/example-form-schema
NG: feature/add-button
NG: fix/バグ修正
NG: kaz/wip
```

issue との紐付けが必要な場合はブランチ名に番号を含める
（`fix/123-fsd-boundary-resolver`）。
