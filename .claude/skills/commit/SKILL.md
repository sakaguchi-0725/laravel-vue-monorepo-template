# コミット

このスキルの目的は、履歴を後から読める資産にすること。そのために2つを外さない。

- **規約どおりのメッセージ** — `references/rules.md` が唯一の正
- **勝手にコミットしない** — 粒度の判断はユーザーに確認してから実行する

## 進め方

### 1. 変更を把握する

```bash
git status
git diff            # 未ステージ
git diff --staged   # ステージ済み
```

差分が大きくて意図が読み取れないときは、該当ファイルを読んで何が変わったのか理解する。
「なぜ変えたか」が分からないままでは body が書けない。この会話の中で自分が行った変更なら、
その経緯がそのまま body の材料になる。

### 2. コミットの粒度とメッセージを検討する

`references/rules.md` を必ず読み、記憶で書かずにその規約に従う。

1. 変更を「なぜこれを変えたか」の理由でグルーピングする
2. 各グループに type を1つ割り当てる。2つ思い浮かぶグループは分割する
3. 各コミット単体で lint と型チェックが通る順序に並べる
4. グループごとにヘッダーと body を書く

### 3. 承認を依頼する

`references/report-format.md` の「コミット承認依頼フォーマット」に従って報告する。
ヘッダー一覧の表示は必須。

`y` 以外が返ってきたら、指摘を反映して再提案する。**承認前にコミットしない。**

### 4. コミットする

グループごとに、意図したパスだけをステージしてコミットする。

```bash
git add <paths>
git commit -m "$(cat <<'EOF'
fix: eslint-config で node:path の型が解決できない問題を修正

TypeScript 6 は node_modules/@types を自動で読み込まなくなったため、
@types/node を追加するだけでは node:path の型が見つからない。

- @types/node を devDependencies に追加
- tsconfig.json の types に node を明示
EOF
)"
```

1ファイルの中で関心事が混ざっていて hunk 単位の分割が必要な場合、対話的な
`git add -p` は使えない。無理に分けず、その旨を伝えてユーザーに判断を仰ぐ。

**pre-commit フックが動く前提で進める。** フックがファイルを整形して差分を書き換える
ことがあるので、コミット後に `git show --stat` で意図したファイルが入っているか確認する。

フックが失敗したら、**そこで止める。** 
`references/report-format.md` の「PreCommitフック失敗報告フォーマット」に
従い、失敗の原因を特定して報告するだけにとどめる。修正はこのスキルの仕事ではない。

### 5. 完了を報告する

`references/report-format.md` の「コミット完了報告フォーマット」に従う。
ヘッダー一覧の表示は必須。push するかを確認し、承認されたら push する。
